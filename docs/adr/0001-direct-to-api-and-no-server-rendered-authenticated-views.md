# The browser calls the API directly, so no authenticated view is server-rendered

The obvious shape for a Next.js application against a separate API is a proxy: the browser calls this application's own origin, and this application's server forwards to the API. It solves two real problems at once — every request becomes same-origin, so CORS stops mattering, and session cookies become first-party, so the cross-site cookie question never arises. It was rejected anyway.

**The browser calls the API directly.** The two problems the proxy would have hidden were fixed where they belonged, in the API: CORS split by credential model, and refresh cookies that survive cross-site. Both were one-line-shaped changes in a repository we own, and both are now verified against the deployed instance. A proxy would have left them unfixed and undiscovered — and the API's own claim is that it serves browser clients on other origins, which is not a claim a proxy can test. This application is now the thing that tests it.

**The consequence is that this application's server holds no credential, and therefore no authenticated view can be server-rendered.** The access token lives in browser memory. The refresh cookie belongs to the API's origin and is invisible here. A server component cannot mint a token, cannot make an authenticated call, and cannot render anything behind a login. Next.js is routing, layout, code-splitting and the build; it is not a rendering strategy for anything that matters.

This is a real cost and it is worth being plain about it. Every authenticated route paints after mount, after a silent credential renewal, and against a free-tier API that sleeps — so the first paint of the dashboard can be tens of seconds behind the first paint of the shell. That is why cold starts are named in the interface rather than spun on: under this decision they are not an edge case, they are the ordinary first experience.

What was weighed against it is smaller than it looks. There is no anonymous content here and nothing to index; every screen is behind a credential. Server-rendering would have bought a faster first paint on pages nobody reaches without signing in first. And the dashboard — the centre of this application — holds a live connection, dedupes envelopes and recovers from replay gaps. It is a client application by nature, and rendering its first frame on a server would not change that.

The rejected middle option deserves naming, because it will occur to the next reader. The client could post its access token to a route handler here, which sets a first-party cookie, letting server components read it and call the API server-side. That is a proxy wearing a disguise: it reintroduces duplicated session state across two servers, adds a re-synchronisation every time the token is renewed, and keeps none of the property that made the direct call worth having.
